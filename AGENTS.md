# Working on Skylight

These instructions apply throughout this repository. Follow the user's explicit task instructions and preserve unrelated work.

## Purpose

Skylight is a portable, vendor-agnostic set of instructions for how an agent behaves. Solve this with the smallest understandable set of rules. Every rule must justify itself against a real failure mode it prevents, not a hypothetical one.

## Behavioral contract

- No module names a vendor, a plugin, or a client. None assumes one either.
- Every fenced block is self-contained. It must make sense pasted alone into a fresh session, with no access to this repository, its README, or any other module.
- No module references this project's own origin, its author, or a specific tool it was generalized from.

## Implementation

- Read the existing modules before adding a new one. A new rule earns its place only if it prevents a failure the existing rules do not already cover.
- Keep the reasoning in prose outside the fence, and the instructions themselves inside it. The fence is what gets pasted; nothing outside it should be load-bearing for the rules to work.
- Prefer one clear rule to three overlapping ones. If two modules would give conflicting instructions in the same session, merge them or make the boundary between them explicit.

## Verification

- Read a module as if seeing it for the first time, in a fresh session, with no access to this repository. If a rule only makes sense because of context from outside its fence, move that context inside the fence or cut the rule.
- Check every fenced block against `core.md`'s own formatting rule: no em dash, prose before lists, plain language. A ruleset that tells an agent to write plainly should not violate that rule itself.

## Writing

- Use familiar words and short explanations. State why a rule exists before stating the rule, so a reader can judge an edge case the rule did not anticipate.
- Do not add personal names, machine file paths, conversation history, or references to a specific project this ruleset was drawn from.
- Do not add AI attribution or "generated by" credits to the documentation or to release text.
- Keep the author field, the working repository links, and the required license notice. Do not invent an author.
- Do not add a co-author line to a commit unless the user asks for one. Use the project's public identity for each commit. Do not guess this identity from a machine username.

## Releases

- Keep experiments local or private; publish only a reviewed snapshot.
- A version change or a publish action must be part of the user's current task. If the user already gave permission for this task, do not ask again.
- Before publication, check the staged files and commit metadata for private data or unintended history. Do not rewrite published history unless the user asks for it.
- Keep the changelog, the release tag, and the release assets consistent with each other.
